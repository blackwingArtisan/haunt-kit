# Design: Scavenger Hunt

- **Routes (hash):** `#/` home, `#/host` editor, `#/play/<code>` player. The hunt lives after `#`, so it is never sent to a server.
- **Draft vs shared:** `HuntDraft` (plain answers, on the host's device) becomes `SharedHunt` (salted digests) through `shareableHunt`. `huntToTour` turns a shared hunt into an engine tour; each stop's challenge answers are `sha256:<salt>:<digest>`, checked by the skeleton's `checkAnswer`.
- **Link format:** `1` + base64url(deflate-raw(JSON compact array)). Coordinates are integer micro-degrees, stops after the first stored as deltas. `0` + base64url(JSON) when `CompressionStream` is missing. A ten-stop hunt with long clues stays under 1,500 characters.
- **Hunt identity:** first 5 bytes of SHA-256 of the code, hex. Keys progress, the active run and the leaderboard.
- **Hot and cold:** `heat(distance, radius)` buckets (here, burning, hot, warm, cool, cold), `heatLevel` for the bar, `trend` with a 4 m dead band.
- **Leaderboard:** `Leaderboard` over `KeyValueStore`, ranked by `elapsed + 30 s × hints + 10 s × wrong answers`, keeps the last 100 runs.
- **Result link ("Send my time to the host"):** route `#/result/<code>`. Code format: `1` + base64url(deflate-raw(JSON)), or `0` + base64url(JSON) without `CompressionStream`. The JSON is a fixed eight-item array `[1, huntId, player, elapsedMs, hints, wrongAnswers, assisted, finishedAt]`, so a result cannot carry anything else: no answers, no digests, no clues and no coordinates. The decoder reuses the base64url and stream helpers exported by `hunt-codec.ts`, rejects any other length, and range-checks every field (name 1 to 40 characters without control characters, a 10-hex-digit hunt id, whole numbers within limits, a finish date between 2020 and 2100). Codes over 600 characters are refused; a real code is about 100 characters.
- **Which hunt is "this hunt":** a result names its hunt by `huntId` (the first 5 bytes of SHA-256 of the hunt code), which is also the leaderboard key. The host's device cannot rebuild the hunt code, because each share link uses a new random salt, so `Host` stores `{ id, title, sharedAt }` under `shared-hunts` when it makes a link (at most 50). A result is accepted only for an id in that list; anything else is "a different hunt".
- **Add and duplicate rule:** `inspectResult` returns `ready`, `wrong-hunt` or `duplicate`; `submitResult` re-checks, then calls `Leaderboard.add`. Two runs are the same when player (as stored), `finishedAt` and `elapsedMs` match. The player's own device already holds the run, so opening the link there reports a duplicate.
- **UI:** `Play` shows a "Send my time to the host" link (the result URL itself, with `data-testid="result-link"`) and a "Copy result link" button under the finished card. `Result.tsx` shows the run, the button or the refusal, and the leaderboard of that hunt. `Scoreboard` moved to its own file so both screens share it.
- **Theme:** cut-paper Halloween party. Creepster for display only, Atkinson Hyperlegible for everything people read, thick ink outlines and offset shadows, pumpkin, slime and grape on a purple night.
- **Testing:** unit tests for codec round-trip, the result codec and host leaderboard rules, compression fallback, answer secrecy, size budget, damaged links, draft issues, leaderboard ranking and hot/cold. E2E: host builds a hunt with a recorded GPS spot and a map pin, shares, player races a simulated walk with a wrong then right answer, leaderboard shows the run; a player finishes from the list, sends the result link, and a host in a second browser context adds it (and a repeat, a damaged link and a different hunt are refused); list unlock with hint; hot/cold meter with real geolocation; damaged link.
